# Workspace

This folder groups the repositories of one product. Use this file for work that spans repositories.
Each repository is self-contained: its own `AGENTS.md`, checks, and wiki rule inside it, and CI or a teammate who clones
a single repository never sees this file. Never move a rule that a repository needs into this file.

## Setting up on another machine

This folder is a git repository of its own; the repositories it lists are cloned from their `remote` in `workspace.json`. Nothing else is needed:

```bash
git clone <this workspace repository> <folder> && cd <folder>
python3 .ai/workspace.py clone --team <team>   # every listed repository that is not here yet, and your team in CLAUDE.local.md
python3 .ai/workspace.py clone --name be       # only the named ones
python3 .ai/workspace.py check                 # personal files tracked by git, or no team recorded
```

It never touches a repository that is already here, skips entries without a remote, and connects the pre-commit verify hook in
repositories with the harness. A repository you cannot access is listed under `failed` and the rest go on; ask for access and run it again.
Run it again after a pull that lists new repositories. Each repository's own setup still follows its README.

## Teams and personal settings

`CLAUDE.local.md` at this root belongs to one person: git ignores it, `python3 .ai/workspace.py local --team <team>` makes it from
`.ai/CLAUDE.local.example.md`, and Claude Code loads it in every session here. Other agents read it before their first task in this folder.
Its `Team:` line names the user's team, one of the `teams` in `workspace.json`.

- A rule or section marked with teams, such as "(dev)", applies only to members of those teams; an unmarked rule applies to everyone.
- With no team recorded, ask for it before a team-marked task, and suggest `python3 .ai/workspace.py local --team <team>`.
- Never write one person's values into a shared file: names, account IDs, personal paths, or anything from `CLAUDE.local.md`.
  Look them up at run time instead, for example the current user from the issue tracker, or keep them in `CLAUDE.local.md`.
- Access to each repository is granted on its remote. Do not work around a repository the user cannot clone or push to.

## Skills

Workspace skills live in `.agents/skills/<name>/SKILL.md`, the only copy; `.claude/skills/<name>` links to it so that Claude Code finds it.
They load in sessions opened at this folder, not in sessions opened inside a repository, which have their own skills.
Other agents read `.agents/skills/<name>/SKILL.md` and follow it when a task matches its description.

- A new member, or a `python3 .ai/workspace.py check` with problems: use `workspace-onboard`.
- Adding a skill: create `.agents/skills/<name>/SKILL.md` with `name: <name>` and a `description` that says when to use it in the frontmatter,
  run `python3 .ai/workspace.py skills sync`, then `check`, and commit both paths only when the user asks. A skill for one team says so in its description.
  Names starting with `workspace-` are reserved for skills that ship with the workspace; their files change only through a starter upgrade.

## Rules

- Before writing in a repository, read that repository's `AGENTS.md`. Its rules win inside it.
- Run checks from inside the repository: `cd <repo> && python3 tool/ai.py verify`. Run from this folder, the CLI finds the wrong root and fails.
- Changing a contract that a repository owns is at least L2 there. Name every consumer repository and what it must change in the completion report,
  and change consumers in their own repositories, as separate tasks with their own verification.
- Commits, branches, and pushes happen per repository and only when the user asks.
- This folder's own git history tracks only this file, `README.md`, `CLAUDE.md`, `workspace.json`, `.gitignore`, and `.claude/`, `.agents/`, `.ai/`;
  repositories are ignored, never submodules. `README.md` is for people: keep its getting-started steps in step with this file.
